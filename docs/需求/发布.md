# 发布

## 现在

- VSPi 2.9.1 已完成 Linux 本地发布准备与完整校验；本阶段不创建 tag、不推送、不发布。版本包、兼容包及校验和位于 `apps/vspi/.tmp/package-artifacts/`。同一 tarball 已在 Node 22.19.0 与 24.16.0 下通过隔离安装和隔离 daemon 启停；分包验收数字见版本记录。
- VSPi 不通过 GitHub Actions 构建或验证发行包。发布前在 Linux 工作机本地完成验证，再用 `scripts/github-release-producer.mjs` 创建 GitHub Release。
- 发版前依次运行全量校验、发布器测试、打包、包校验和打包 daemon 冒烟：
  - `pnpm run check:vspi`
  - `node --test scripts/github-release-producer.test.mjs`
  - `pnpm --filter vspi package:pack`
  - `pnpm --filter vspi package:verify`
- 发布产物与验证过的 tarball 逐字节一致，校验和由被验证的文件生成。
- 版本号、tag 和 `apps/vspi/package.json` 的一致性由 `scripts/vspi-release-identity.mjs` 校验。producer 不覆盖同名的 tag 或资产。
- `vspi update` 从共享的 `latest` 标签定位版本化 tgz，并校验 `SHA256SUMS`。
- 当前按 Linux 先行发布，Windows 和 macOS 的验收范围按当次实际结果记录；没有验收的平台不写成已通过。
- VSPi 使用独立的 tag 发布流程，不创建 Kimi Code 的 changeset。

## 规则

- 只发布本地验证过的同一个 tarball，不在发布机上重新构建。
- 发版前必须跑 `check:vspi`，不能只跑 VSPi 包的测试。
- 发布说明写适用平台、安装方式、风险和实际验收范围。
- 已经发布的版本不能换字节；需要修复时发新版本。
- 发布和反馈、分发节点的部署是两个独立授权步骤。

## 不能坏

- 不能把未验收的平台写成已通过。
- 不能在 tag、版本号和包内容不一致时发布。
- 不能覆盖已经发布的 tag 或同名资产。
- 不能跳过校验和生成，也不能让更新通道指向没有完成校验的包。

## 牵连

- daemon 与 IPC：运行时构建标识、入口文件和最低 Node 版本必须与发行包一致。
- 会话与对话：发布说明中的行为和实际安装包一致。
- 文档站：版本记录和使用说明随版本更新。
